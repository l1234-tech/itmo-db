# Теория к лабораторной работе № 2

Конспект по вопросам к защите: строки и шаблоны, соединения, операции над множествами, подзапросы, последовательности, оконные функции, CTE и представления. Примеры ориентированы на PostgreSQL.

## 1. Результат выполнения запроса

SELECT возвращает набор строк и столбцов. Если совпадений нет, результат содержит 0 строк — это не обязательно синтаксическая ошибка. Диагностировать удобно последовательно: проверить исходную таблицу, условия ON, WHERE, значения ключей, типы, NULL, затем группировки и HAVING.

    SELECT Н_ОБУЧЕНИЯ.*
    FROM Н_ОБУЧЕНИЯ
    WHERE НЗК = '999080';

## 2. LIKE и ILIKE

LIKE — сравнение со строковым шаблоном; ILIKE — расширение PostgreSQL для сравнения без учёта регистра. Символ % означает любую последовательность символов, в том числе пустую; _ — ровно один символ.

    SELECT * FROM Н_ЛЮДИ WHERE ФАМИЛИЯ LIKE 'Иван%';
    SELECT * FROM Н_ЛЮДИ WHERE ФАМИЛИЯ ILIKE '%ов';
    SELECT * FROM Н_ЛЮДИ WHERE ИМЯ LIKE '_ля';

Чтобы искать буквальные % и _, задают escape-символ через ESCAPE.

## 3. CHAR, VARCHAR, TEXT и to_char

- CHAR(n) — строка фиксированной длины; короткие значения дополняются пробелами.
- VARCHAR(n) — строка переменной длины с ограничением длины.
- TEXT — строка переменной длины без заданного ограничения в объявлении.

В PostgreSQL VARCHAR(n) обычно не быстрее TEXT; ограничения длины имеет смысл задавать, когда они являются требованием предметной области.

Приведение значения к тексту через ::text или CAST(... AS text) даёт обычное текстовое представление. to_char форматирует числа и даты по заданной маске:

    SELECT 1234.5::text;
    SELECT to_char(1234.5, 'FM9999.00');
    SELECT to_char(CURRENT_DATE, 'DD.MM.YYYY');

Используйте to_char для контролируемого формата отображения. Для вычислений и условий лучше сохранять значения в числовом или временном типе.

## 4. Виды JOIN

JOIN комбинирует строки из таблиц по условию соединения.

    -- INNER JOIN: только совпавшие строки
    SELECT l.ИД, o.НЗК
    FROM Н_ЛЮДИ AS l
    JOIN Н_ОБУЧЕНИЯ AS o ON o.ЧЛВК_ИД = l.ИД;

    -- LEFT JOIN: все строки слева, при отсутствии пары поля справа равны NULL
    SELECT l.ИД, o.НЗК
    FROM Н_ЛЮДИ AS l
    LEFT JOIN Н_ОБУЧЕНИЯ AS o ON o.ЧЛВК_ИД = l.ИД;

    -- RIGHT JOIN: сохраняет все строки правого источника
    SELECT l.ИД, o.НЗК
    FROM Н_ЛЮДИ AS l
    RIGHT JOIN Н_ОБУЧЕНИЯ AS o ON o.ЧЛВК_ИД = l.ИД;

    -- FULL OUTER JOIN: все строки обеих сторон
    SELECT l.ИД, o.ЧЛВК_ИД
    FROM Н_ЛЮДИ AS l
    FULL OUTER JOIN Н_ОБУЧЕНИЯ AS o ON o.ЧЛВК_ИД = l.ИД;

    -- CROSS JOIN: декартово произведение
    SELECT a.ИД, b.ИД FROM таблица_a AS a CROSS JOIN таблица_b AS b;

INNER можно опустить, написав просто JOIN. LEFT OUTER эквивалентен LEFT, RIGHT OUTER — RIGHT, FULL OUTER — FULL. CROSS JOIN образует каждую комбинацию строк; при M строках в первой таблице и N во второй результат содержит M × N строк.

### ON, USING и NATURAL JOIN

ON задаёт произвольное условие. USING (столбец) сокращает синтаксис, если столбец с одинаковым именем присутствует с обеих сторон; общий столбец выводится один раз.

    SELECT * FROM заказы JOIN клиенты USING (клиент_id);
    SELECT * FROM заказы JOIN клиенты ON заказы.клиент_id = клиенты.id;

NATURAL JOIN автоматически соединяет по всем одноимённым столбцам. Это хрупкое решение: добавление одноимённого столбца может незаметно изменить смысл. Обычно лучше явно указывать ON или USING.

### ON и WHERE при OUTER JOIN

ON определяет, какие строки признаются совпавшими; WHERE фильтрует итог после соединения. Условие по правой таблице в WHERE способно отбросить строки, для которых справа NULL, и сделать результат похожим на INNER JOIN.

    SELECT l.ИД, o.НЗК
    FROM Н_ЛЮДИ l
    LEFT JOIN Н_ОБУЧЕНИЯ o
      ON o.ЧЛВК_ИД = l.ИД AND o.НЗК = '999080';

Этот запрос сохраняет людей даже тогда, когда у них нет обучения с указанным НЗК.

## 5. UNION, UNION ALL, INTERSECT и EXCEPT

Эти операции сопоставляют строки двух результатов запросов. Количество столбцов должно совпадать, а типы соответствующих столбцов быть совместимыми.

    SELECT имя FROM студенты
    UNION
    SELECT имя FROM преподаватели;

    SELECT имя FROM студенты
    UNION ALL
    SELECT имя FROM преподаватели;

    SELECT имя FROM студенты
    INTERSECT
    SELECT имя FROM участников_курса;

    SELECT имя FROM студенты
    EXCEPT
    SELECT имя FROM участников_курса;

- UNION объединяет результаты и удаляет дубликаты.
- UNION ALL объединяет без удаления дубликатов и обычно дешевле.
- INTERSECT оставляет строки, имеющиеся в обоих результатах.
- EXCEPT оставляет строки первого результата, отсутствующие во втором.

Для удаления дубликатов в операциях над множествами совпадающие строки с NULL могут считаться неразличимыми, и повторяющиеся строки схлопываются. Поэтому UNION без ALL может вернуть одну строку вместо нескольких одинаковых строк, содержащих NULL.

JOIN расширяет строки столбцами из связанных таблиц. UNION, INTERSECT и EXCEPT работают с совместимыми результатами запросов по позициям столбцов — это не взаимозаменяемые механизмы.

## 6. CASE

CASE — выражение, которое возвращает значение первой подходящей ветви; все возможные результаты должны приводиться к совместимому типу.

**Простая форма** сопоставляет одно выражение со значениями:

    SELECT CASE статус
             WHEN 'A' THEN 'активен'
             WHEN 'D' THEN 'удалён'
             ELSE 'неизвестен'
           END
    FROM сущности;

**Поисковая форма** проверяет логические условия:

    SELECT CASE
             WHEN балл >= 90 THEN 'отлично'
             WHEN балл >= 70 THEN 'хорошо'
             WHEN балл IS NULL THEN 'нет оценки'
             ELSE 'нужно повторить'
           END
    FROM результаты;

## 7. NOT IN и NOT EXISTS

NOT EXISTS истинно, если подзапрос не вернул ни одной строки. NOT IN сравнивает левое выражение с набором справа. Если подзапрос NOT IN содержит NULL, итог может быть UNKNOWN и строка не пройдёт WHERE.

    SELECT l.*
    FROM Н_ЛЮДИ l
    WHERE NOT EXISTS (
        SELECT 1 FROM Н_ОБУЧЕНИЯ o WHERE o.ЧЛВК_ИД = l.ИД
    );

Анти-join обычно надёжнее выражать через NOT EXISTS, потому что он напрямую означает отсутствие соответствующей строки и не имеет ловушки NULL в списке.

## 8. Подзапросы и упрощение запросов

Подзапрос бывает скалярным (одно значение), возвращающим один столбец или табличный результат. Коррелированный подзапрос ссылается на строку внешнего запроса.

Для удобства используют алиасы таблиц, явные списки столбцов, CTE с WITH, удаление ненужных JOIN и EXISTS вместо JOIN, когда нужна только проверка существования. Производительность оценивают по плану, например EXPLAIN (ANALYZE, BUFFERS), а не только по внешнему виду SQL.

## 9. Операция деления в реляционной алгебре

Деление отвечает на вопрос «найти такие X, которые связаны со всеми элементами набора Y». Например, найти студентов, сдавших все обязательные дисциплины. В SQL это можно выразить двойным NOT EXISTS:

    SELECT s.студент_id
    FROM студенты s
    WHERE NOT EXISTS (
        SELECT 1
        FROM обязательные_дисциплины d
        WHERE NOT EXISTS (
            SELECT 1
            FROM результаты r
            WHERE r.студент_id = s.студент_id
              AND r.дисциплина_id = d.дисциплина_id
              AND r.сдано = TRUE
        )
    );

Смысл: не существует обязательной дисциплины, для которой не существует успешного результата этого студента.

## 10. GROUP BY, HAVING, GROUPING SETS, ROLLUP и CUBE

WHERE фильтрует строки до группировки; GROUP BY формирует группы; HAVING фильтрует группы после расчёта агрегатов.

    SELECT группа, COUNT(*) AS число
    FROM студенты
    WHERE дата_зачисления >= DATE '2025-09-01'
    GROUP BY группа
    HAVING COUNT(*) > 10;

GROUPING SETS позволяет задать несколько комбинаций группировок в одном запросе:

    SELECT факультет, группа, COUNT(*)
    FROM студенты
    GROUP BY GROUPING SETS ((факультет, группа), (факультет), ());

ROLLUP(a, b, c) создаёт иерархические итоги: (a,b,c), (a,b), (a), (). CUBE(a,b) создаёт все комбинации подмножеств: (a,b), (a), (b), ().

    SELECT факультет, группа, COUNT(*)
    FROM студенты
    GROUP BY ROLLUP (факультет, группа);

В итоговых строках свёрнутые уровни показываются как NULL; GROUPING(столбец) помогает отличить такой NULL от настоящего NULL в данных.

## 11. CTE и рекурсивные запросы

### Что такое CTE

CTE (Common Table Expression) — именованный промежуточный результат, который объявляется через WITH и используется в основном запросе. Он помогает разбить большой запрос на логические шаги.

    WITH активные AS (
        SELECT *
        FROM студенты
        WHERE статус = 'учится'
    )
    SELECT группа, COUNT(*) AS количество
    FROM активные
    GROUP BY группа;

Имя активные существует только в пределах этого одного SQL-запроса. CTE не является автоматически постоянной таблицей.

### Что такое рекурсивный запрос

Рекурсивный запрос нужен, когда данные имеют повторяющуюся структуру: подразделение и его подчинённые подразделения, папка и вложенные папки, категория и подкатегории, сотрудник и руководитель. В PostgreSQL для него используется WITH RECURSIVE.

Стандартная структура:

    WITH RECURSIVE дерево AS (
        -- Начальная (базовая) часть: откуда начинаем обход
        SELECT ...

        UNION ALL

        -- Рекурсивная часть: как получить следующий уровень
        SELECT ...
        FROM исходная_таблица AS child
        JOIN дерево AS parent ON ...
    )
    SELECT *
    FROM дерево;

У рекурсивного CTE есть три ключевых элемента:

1. **Начальная часть** (anchor) находит исходные строки. При обходе дерева от корней это обычно строки, у которых parent_id IS NULL.
2. **UNION ALL** объединяет начальную часть с результатами рекурсивной части. В типичных обходах используют именно UNION ALL, чтобы не запускать удаление дубликатов на каждой итерации.
3. **Рекурсивная часть** читает строки из самого CTE предыдущего шага и присоединяет к ним следующие строки исходной таблицы.

У обеих частей SELECT должно совпадать количество столбцов, а типы соответствующих столбцов должны быть совместимы. Поля, которые вычисляются по мере обхода, инициализируют в начальной части: например, глубину значением 0, путь — названием корня.

### Как работает рекурсия по шагам

Допустим, таблица подразделений хранит ID родителя:

| id | name | parent_id |
|---:|---|---:|
| 1 | Университет | NULL |
| 2 | Институт A | 1 |
| 3 | Кафедра A1 | 2 |
| 4 | Кафедра A2 | 2 |

Начальная часть получает только Университет. Первая итерация находит Институт A, потому что его parent_id = 1. Следующая итерация находит Кафедра A1 и Кафедра A2, поскольку их parent_id = 2. Затем новых потомков нет и обход завершается.

Ключевое условие перехода обычно выглядит так:

    child.parent_id = parent.id

Здесь child — новая строка из исходной таблицы, а parent — уже найденная строка из рекурсивного CTE. Это условие означает «найти детей текущего родителя».

### Путь и глубина

Глубина корня обычно равна 0. На каждом следующем уровне она увеличивается на единицу:

    0 AS depth
    parent.depth + 1 AS depth

Путь строят последовательным соединением названий:

    name::text AS path
    parent.path || ' / ' || child.name AS path

Оператор || соединяет текст. Приведение к text полезно, чтобы PostgreSQL точно вывел текстовый тип для пути.

### Рекурсивный запрос для иерархии подразделений из «Учебного процесса»

В схеме учебной базы для иерархии используется таблица Н_ОТДЕЛЫ с идентификатором ИД и предполагаемым родительским идентификатором ОТД_ИД. Привязка считается подтверждённой только после проверки внешнего ключа в конкретной базе. Запрос ниже предполагает, что корни имеют ОТД_ИД IS NULL; фактические данные следует проверить до выполнения.

    WITH RECURSIVE иерархия AS (
        -- 1. Начинаем с корневых подразделений
        SELECT
            o.ИД,
            o.ОТД_ИД,
            o.КОРОТКОЕ_ИМЯ,
            0 AS ГЛУБИНА,
            COALESCE(
                NULLIF(o.ИМЯ_В_ИМИН_ПАДЕЖЕ, ''),
                o.КОРОТКОЕ_ИМЯ
            )::TEXT AS ПОЛНЫЙ_ПУТЬ,
            ARRAY[o.ИД] AS ПОСЕЩЁННЫЕ
        FROM Н_ОТДЕЛЫ AS o
        WHERE o.ОТД_ИД IS NULL

        UNION ALL

        -- 2. Находим дочерние подразделения
        SELECT
            child.ИД,
            child.ОТД_ИД,
            child.КОРОТКОЕ_ИМЯ,
            parent.ГЛУБИНА + 1,
            parent.ПОЛНЫЙ_ПУТЬ || ' -> ' ||
                COALESCE(
                    NULLIF(child.ИМЯ_В_ИМИН_ПАДЕЖЕ, ''),
                    child.КОРОТКОЕ_ИМЯ
                ),
            parent.ПОСЕЩЁННЫЕ || child.ИД
        FROM Н_ОТДЕЛЫ AS child
        JOIN иерархия AS parent
            ON child.ОТД_ИД = parent.ИД
        WHERE NOT (child.ИД = ANY(parent.ПОСЕЩЁННЫЕ))
    )
    SELECT
        ИД,
        ОТД_ИД,
        КОРОТКОЕ_ИМЯ,
        ПОЛНЫЙ_ПУТЬ,
        ГЛУБИНА
    FROM иерархия
    ORDER BY ПОЛНЫЙ_ПУТЬ;

### Разбор запроса по частям

- Начальная часть выбирает корни через WHERE ОТД_ИД IS NULL. Для них ГЛУБИНА равна 0, а ПОЛНЫЙ_ПУТЬ начинается с названия самого подразделения.
- UNION ALL добавляет к корням строки, полученные рекурсивным шагом.
- Условие child.ОТД_ИД = parent.ИД находит непосредственных детей каждого уже найденного подразделения.
- parent.ГЛУБИНА + 1 увеличивает уровень на единицу.
- parent.ПОЛНЫЙ_ПУТЬ || ' -> ' || ... дописывает имя ребёнка в конец пути от корня.
- COALESCE(NULLIF(имя, ''), КОРОТКОЕ_ИМЯ) использует имя в именительном падеже, если оно задано и не пустое; иначе используется короткое имя.
- Массив ПОСЕЩЁННЫЕ сохраняет идентификаторы на текущем пути. Условие NOT (child.ИД = ANY(parent.ПОСЕЩЁННЫЕ)) не позволяет повторно пройти уже посещённый ID по тому же пути, защищая запрос от бесконечного цикла в данных.

Проверить наличие корневых подразделений:

    SELECT ИД, ОТД_ИД, КОРОТКОЕ_ИМЯ
    FROM Н_ОТДЕЛЫ
    WHERE ОТД_ИД IS NULL;

Проверить определения внешних ключей таблицы (запрос предполагает, что схема с таблицей доступна через search_path):

    SELECT conname, pg_get_constraintdef(oid)
    FROM pg_constraint
    WHERE conrelid = 'н_отделы'::regclass
      AND contype = 'f';

Если первый запрос не возвращает строк, возможно, корни обозначены иначе или столбец ОТД_ИД не является тем полем, которое задаёт родителя. В таком случае нельзя просто менять условие наугад: нужно посмотреть ограничения и реальные значения.

### Частые ошибки в рекурсивных запросах

1. Неправильное имя столбца. В этой схеме используется ИМЯ_В_ИМИН_ПАДЕЖЕ, а не ИМЯ_В_ИМ_ПАДЕЖЕ.
2. Несовпадающее число или несовместимые типы столбцов в двух частях UNION ALL.
3. Неправильное условие JOIN: если перепутать ID текущего элемента и ID родителя, обход не найдёт потомков.
4. Неправильное начальное условие: если корни не выбраны, результат может быть пустым даже при наличии данных.
5. Циклы в иерархии могут вызывать повторный обход. Массив посещённых ID в приведённом запросе служит защитой для пути, по которому идёт обход.

## 12. Последовательности

Последовательность — объект, выдающий числовые значения. nextval выдаёт новое значение; currval возвращает значение, уже полученное этой сессией через nextval; setval изменяет состояние.

    CREATE SEQUENCE order_id_seq START 1 INCREMENT 1 CACHE 10;
    SELECT nextval('order_id_seq');
    SELECT currval('order_id_seq');
    SELECT setval('order_id_seq', 100, true);
    ALTER SEQUENCE order_id_seq INCREMENT BY 2 CACHE 20;
    ALTER SEQUENCE order_id_seq RESTART WITH 1;

Параметры можно менять через ALTER SEQUENCE. CACHE резервирует значения для производительности; при аварии часть закэшированных номеров может пропасть. Удаление строки обычно не возвращает её ID в последовательность. Сбрасывать sequence следует только с учётом зависимостей и параллельных транзакций.

## 13. Оконные функции; ROW_NUMBER, RANK, DENSE_RANK

### Что такое оконная функция

Оконная функция вычисляет значение для текущей строки на основе некоторого набора связанных строк, но не сворачивает строки, как GROUP BY. В PostgreSQL окно задаётся конструкцией OVER.

    SELECT
        студент_id,
        группа,
        балл,
        AVG(балл) OVER (PARTITION BY группа) AS средний_балл_группы
    FROM результаты;

Каждый студент остаётся отдельной строкой, но рядом с его баллом появляется средний балл всей группы.

Основные части OVER:

- PARTITION BY разделяет строки на независимые окна, например по группе.
- ORDER BY задаёт порядок строк внутри окна для расчёта.
- Рамка окна задаётся ROWS или RANGE и ограничивает строки, которые учитываются функцией. Рамка нужна прежде всего оконным агрегатам и некоторым другим функциям.

### Оконная функция и GROUP BY

GROUP BY сворачивает исходные строки и возвращает, как правило, одну строку на группу:

    SELECT группа, AVG(балл) AS средний_балл
    FROM результаты
    GROUP BY группа;

Оконная функция сохраняет исходные строки:

    SELECT
        студент_id,
        группа,
        балл,
        AVG(балл) OVER (PARTITION BY группа) AS средний_балл
    FROM результаты;

Первый запрос даёт сводку по группам. Второй даёт средний балл каждой группы в каждой строке студента.

### ROW_NUMBER, RANK и DENSE_RANK

Пример набора оценок: 95, 90, 90, 70.

    SELECT
        студент_id,
        балл,
        ROW_NUMBER() OVER (ORDER BY балл DESC, студент_id) AS номер,
        RANK() OVER (ORDER BY балл DESC) AS ранг,
        DENSE_RANK() OVER (ORDER BY балл DESC) AS плотный_ранг
    FROM результаты;

- ROW_NUMBER присваивает уникальные порядковые номера строкам: 1, 2, 3, 4. При равных баллах порядок будет произвольным, если не добавить дополнительный критерий, например студент_id.
- RANK присваивает одинаковый ранг строкам с одинаковым значением и пропускает следующие номера: 1, 2, 2, 4.
- DENSE_RANK тоже даёт равным строкам одинаковый ранг, но не пропускает номер: 1, 2, 2, 3.

PARTITION BY можно использовать, если места нужно считать внутри каждой группы:

    RANK() OVER (
        PARTITION BY группа
        ORDER BY балл DESC
    )

### Чем ORDER BY отличается от оконной функции с ORDER BY

Это принципиальное различие. ORDER BY внутри OVER управляет вычислением оконной функции, но не гарантирует порядок строк в окончательном выводе. Внешний ORDER BY сортирует итоговый результат.

Допустим, исходная таблица students:

| id | name | score |
|---:|---|---:|
| 1 | Анна | 70 |
| 2 | Борис | 95 |
| 3 | Вера | 85 |
| 4 | Глеб | 95 |
| 5 | Дима | 60 |

Запрос рассчитывает номер места по убыванию оценки, но выводит строки по id:

    SELECT
        id,
        name,
        score,
        ROW_NUMBER() OVER (
            ORDER BY score DESC, id
        ) AS place
    FROM students
    ORDER BY id;

Результат:

| id | name | score | place |
|---:|---|---:|---:|
| 1 | Анна | 70 | 4 |
| 2 | Борис | 95 | 1 |
| 3 | Вера | 85 | 3 |
| 4 | Глеб | 95 | 2 |
| 5 | Дима | 60 | 5 |

Места вычислены по score DESC, но строки в результирующем наборе упорядочены по id. Если написать только ORDER BY score DESC, строки отсортируются по оценке, но новые номера мест не появятся. Если написать только ROW_NUMBER() OVER (ORDER BY score DESC), номера появятся, но порядок итоговых строк без внешнего ORDER BY SQL не гарантирует.

Чтобы и посчитать места, и вывести строки по оценке:

    SELECT
        id,
        name,
        score,
        ROW_NUMBER() OVER (
            ORDER BY score DESC, id
        ) AS place
    FROM students
    ORDER BY score DESC, id;

### Агрегатные оконные функции и накопительный итог

Агрегаты SUM, AVG, COUNT, MIN и MAX можно использовать с OVER. Например, накопительный итог продаж:

    SELECT
        дата,
        сумма,
        SUM(сумма) OVER (
            ORDER BY дата, сумма
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS накопительная_сумма
    FROM продажи
    ORDER BY дата, сумма;

В этом примере каждая следующая строка прибавляет свою сумму к уже накопленному итогу. В ORDER BY добавлен второй критерий сумма, чтобы задать более стабильный порядок при одинаковой дате.

### ROWS и RANGE: рамка окна

ROWS и RANGE задают, какие строки учитывает оконная функция относительно текущей строки.

- ROWS считает физические строки в порядке, заданном оконным ORDER BY. Например, ROWS BETWEEN 2 PRECEDING AND CURRENT ROW включает две предыдущие строки и текущую — максимум три строки.
- RANGE ориентируется на значение сортировочного выражения. Строки с одинаковыми значениями ORDER BY являются строками-сверстниками (peers) и для текущей рамки RANGE могут учитываться вместе.

Типовые границы рамки:

- UNBOUNDED PRECEDING — начало окна.
- n PRECEDING — n строк назад для ROWS или соответствующее смещение значения для RANGE.
- CURRENT ROW — текущая строка; для RANGE учитываются также строки-сверстники текущего значения.
- n FOLLOWING — смещение вперёд.
- UNBOUNDED FOLLOWING — конец окна.

### Пример, показывающий различие ROWS и RANGE

    WITH продажи (дата, сумма) AS (
        VALUES
            (DATE '2026-10-01', 10),
            (DATE '2026-10-02', 5),
            (DATE '2026-10-02', 7),
            (DATE '2026-10-03', 3)
    )
    SELECT
        дата,
        сумма,
        SUM(сумма) OVER (
            ORDER BY дата, сумма
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS итог_rows,
        SUM(сумма) OVER (
            ORDER BY дата
            RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS итог_range
    FROM продажи
    ORDER BY дата, сумма;

Ожидаемый результат:

| дата | сумма | итог_rows | итог_range |
|---|---:|---:|---:|
| 2026-10-01 | 10 | 10 | 10 |
| 2026-10-02 | 5 | 15 | 22 |
| 2026-10-02 | 7 | 22 | 22 |
| 2026-10-03 | 3 | 25 | 25 |

У ROWS для второй записи итог равен 15, а для третьей — 22: строки обрабатываются по одной. У RANGE обе строки имеют одну и ту же дату, поэтому в рамку для каждой из них входят обе продажи за 2 октября; обе получают 22.

### Пример скользящего окна

Чтобы получить скользящую сумму не более чем по семи физическим строкам:

    SUM(сумма) OVER (
        ORDER BY дата, id
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    )

Это до семи наблюдений, а не обязательно семь календарных дней. Если задача требует сумму в диапазоне последних семи дней, а не последних семи строк, логически подходит RANGE со смещением интервала и сортировкой по дате:

    SUM(сумма) OVER (
        ORDER BY дата
        RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW
    )

В этом случае учитываются строки с датой в соответствующем диапазоне календарных значений; число строк в рамке может быть любым.

### Рамка по умолчанию

В PostgreSQL для оконного агрегата с ORDER BY и без явно заданной рамки стандартная рамка включает строки от начала окна до текущей строки и её строк-сверстников. Поэтому SUM(...) OVER (ORDER BY дата) может дать одинаковый накопительный итог для всех строк с одной датой.

Если нужно строго построчное накопление, указывай ROWS явно и добавляй устойчивый дополнительный критерий сортировки, например уникальный id.

### Кратко для защиты

Оконная функция не заменяет сортировку результата. ORDER BY внутри OVER задаёт порядок вычисления оконных значений; внешний ORDER BY определяет видимый порядок строк. ROWS задаёт рамку по физическим строкам, RANGE — по значениям сортировки с учётом строк-сверстников. При дубликатах значения ORDER BY RANGE часто даёт одинаковый результат для таких строк, а ROWS может дать разный.
## 14. VIEW и MATERIALIZED VIEW

**VIEW** — сохранённый запрос; результат обычно не хранится отдельно и пересчитывается при обращении. Изменения базовых таблиц видны при следующем запросе к представлению.

    CREATE VIEW публичные_студенты AS
    SELECT id, имя, группа
    FROM студенты
    WHERE открыт = TRUE;

**MATERIALIZED VIEW** хранит результат запроса физически. Чтение может быть быстрее, но данные устаревают до обновления.

    CREATE MATERIALIZED VIEW статистика_групп AS
    SELECT группа, COUNT(*) AS количество
    FROM студенты
    GROUP BY группа;

    REFRESH MATERIALIZED VIEW статистика_групп;

REFRESH MATERIALIZED VIEW CONCURRENTLY уменьшает блокировку читателей, но требует подходящего уникального индекса и имеет дополнительные условия.

### Как представления влияют на производительность

Обычный VIEW не кэширует результат. Оптимизатор может встроить запрос представления в основной план. Сложные JOIN и агрегации всё равно могут быть дорогими; VIEW полезно для повторного использования и понятности кода. MATERIALIZED VIEW ускоряет повторное чтение дорогостоящего результата ценой дополнительного хранения и затрат на обновление.

### Автоматическая обновляемость и WITH CHECK OPTION

Простое представление над одной таблицей без GROUP BY, агрегатных функций, DISTINCT и других усложнений часто обновляемо автоматически. Это означает, что INSERT, UPDATE или DELETE через VIEW может изменять соответствующие строки базовой таблицы.

WITH CHECK OPTION добавляет правило: любые строки, которые вставляются или изменяются через представление, должны продолжать соответствовать его условию WHERE.

Предположим, есть таблица студентов со столбцами id, имя и статус. Создадим представление только для учащихся:

    CREATE VIEW активные_студенты AS
    SELECT id, имя, статус
    FROM студенты
    WHERE статус = 'учится'
    WITH CHECK OPTION;

Такая вставка соответствует фильтру и допустима, если не нарушает другие ограничения таблицы:

    INSERT INTO активные_студенты (id, имя, статус)
    VALUES (10, 'Мария', 'учится');

Такая вставка через представление нарушает фильтр и будет отклонена:

    INSERT INTO активные_студенты (id, имя, статус)
    VALUES (11, 'Олег', 'отчислен');

Аналогично, если существующая строка видна через представление:

    UPDATE активные_студенты
    SET статус = 'отчислен'
    WHERE id = 10;

операция будет отклонена: после изменения строка больше не удовлетворяет условию статус = 'учится'.

### Что именно гарантирует и чего не гарантирует WITH CHECK OPTION

- Контролирует вставку и изменение строк, выполняемые через это представление.
- Не запрещает менять базовую таблицу напрямую, обходя представление.
- Не является проверкой всех ограничений БД вместо PRIMARY KEY, FOREIGN KEY, NOT NULL или CHECK — эти ограничения продолжают действовать отдельно.
- Не делает автоматически обновляемым сложное представление, которое само по себе не поддерживает обновление.
- Для простого представления условие WHERE определяет множество видимых строк, а CHECK OPTION гарантирует, что операция через VIEW не отправит строку за пределы этого множества.

**Как объяснить преподавателю:** WITH CHECK OPTION — это ограничение представления, которое требует, чтобы новые или изменённые через VIEW строки после операции продолжали удовлетворять его условию WHERE.

### INSTEAD OF-триггеры для необновляемого представления

Для сложного VIEW можно создать INSTEAD OF INSERT, UPDATE и DELETE триггер. Функция должна менять базовые таблицы, а затем возвращать NEW для вставки/изменения или OLD для удаления. Ниже общий шаблон — имена таблиц и столбцов следует адаптировать к конкретной схеме.

    CREATE FUNCTION view_dml_trigger()
    RETURNS trigger
    LANGUAGE plpgsql
    AS $$
    BEGIN
        IF TG_OP = 'INSERT' THEN
            INSERT INTO базовая_таблица (id, имя)
            VALUES (NEW.id, NEW.имя);
            RETURN NEW;
        ELSIF TG_OP = 'UPDATE' THEN
            UPDATE базовая_таблица
            SET имя = NEW.имя
            WHERE id = OLD.id;
            RETURN NEW;
        ELSIF TG_OP = 'DELETE' THEN
            DELETE FROM базовая_таблица WHERE id = OLD.id;
            RETURN OLD;
        END IF;
        RETURN NULL;
    END;
    $$;

    CREATE TRIGGER сложное_view_dml
    INSTEAD OF INSERT OR UPDATE OR DELETE ON сложное_view
    FOR EACH ROW EXECUTE FUNCTION view_dml_trigger();

После создания нужно продемонстрировать INSERT, UPDATE и DELETE через VIEW и отдельными SELECT проверить, что изменения попали в нужные базовые таблицы. Это шаблон, а не готовое решение для неизвестной структуры: реальная функция зависит от ключей, defaults и способа отображения строк.

## 15. Поиск в PostgreSQL

Для простого текстового шаблона используют LIKE или ILIKE. Для регулярных выражений PostgreSQL предоставляет ~ (с учётом регистра) и ~* (без учёта регистра). Для полнотекстового поиска применяют tsvector, tsquery, to_tsvector, plainto_tsquery и, при необходимости, GIN-индекс.

    SELECT * FROM статьи WHERE заголовок ILIKE '%postgres%';
    SELECT * FROM статьи WHERE заголовок ~* 'postgres|sql';
    SELECT * FROM статьи
    WHERE to_tsvector('russian', текст)
          @@ plainto_tsquery('russian', 'базы данных');

Условие ILIKE '%текст%' обычно не использует обычный B-tree индекс для поиска подстроки; тип индекса подбирается под вид поиска.

## 16. DELETE, транзакции и autocommit

DELETE без WHERE удаляет все строки таблицы. Перед опасным удалением сначала выполните SELECT с таким же WHERE и проверьте набор строк.

    BEGIN;
    DELETE FROM студенты WHERE статус = 'ошибочная запись';
    -- Проверить результат
    ROLLBACK; -- либо COMMIT, если всё верно

В режиме autocommit клиент автоматически фиксирует каждую успешную команду отдельной транзакцией. ROLLBACK уже не отменит изменение, которое клиент ранее зафиксировал. Точное поведение зависит от настройки клиента и способа запуска команд.

## 17. Краткое сравнение механизмов

| Механизм | Назначение |
|---|---|
| JOIN | Комбинировать связанные строки из разных источников |
| UNION | Объединять совместимые результаты и удалять дубликаты |
| UNION ALL | Объединять результаты, сохраняя дубликаты |
| CTE | Называть промежуточный результат в пределах запроса |
| VIEW | Сохранять запрос для повторного использования |
| MATERIALIZED VIEW | Хранить результат запроса до обновления |
| EXISTS | Проверять наличие хотя бы одной строки |
| NOT EXISTS | Проверять отсутствие подходящих строк |


## 18. Материализованное представление на основе задания 7

Задание 7 ищет людей, которые не являются студентами факультета КТиУ. Этот результат можно хранить в materialized view, чтобы не выполнять подзапрос заново при каждом чтении.

    CREATE MATERIALIZED VIEW люди_не_студенты_ктиу AS
    SELECT l.ИД, l.ФАМИЛИЯ, l.ИМЯ, l.ОТЧЕСТВО
    FROM Н_ЛЮДИ AS l
    WHERE NOT EXISTS (
        SELECT 1
        FROM Н_УЧЕНИКИ AS u
        JOIN Н_ПЛАНЫ AS p ON u.ПЛАН_ИД = p.ИД
        JOIN Н_ОТДЕЛЫ AS o ON p.ОТД_ИД = o.ИД
        WHERE u.ЧЛВК_ИД = l.ИД
          AND o.КОРОТКОЕ_ИМЯ = 'КТиУ'
    );

    SELECT * FROM люди_не_студенты_ктиу;
    REFRESH MATERIALIZED VIEW люди_не_студенты_ктиу;

Представление сохраняет результат на момент создания/последнего REFRESH, поэтому после изменения базовых данных его нужно обновлять. Для REFRESH MATERIALIZED VIEW CONCURRENTLY понадобится подходящий уникальный индекс, например на ИД, если это действительно уникальный идентификатор результата.


## 19. Рекурсивный запрос для иерархии подразделений из БД «Учебный процесс»

В ER-диаграмме базы присутствует таблица `Н_ОТДЕЛЫ` со столбцами `ИД`, `КОРОТКОЕ_ИМЯ`, `ИМЯ_В_ИМИН_ПАДЕЖЕ` и `ОТД_ИД`. Для иерархического обхода `ОТД_ИД` используется как идентификатор родительского подразделения, а `ИД` — идентификатор самого подразделения.

Запрос ниже предполагает, что корневые записи имеют `ОТД_ИД IS NULL`. Если схема или данные конкретного экземпляра БД отличаются, перед использованием следует проверить внешний ключ и наличие корневых строк.

    WITH RECURSIVE иерархия AS (
        -- Начальная часть: корневые подразделения
        SELECT
            o.ИД,
            o.ОТД_ИД,
            o.КОРОТКОЕ_ИМЯ,
            o.ИМЯ_В_ИМИН_ПАДЕЖЕ,
            0 AS ГЛУБИНА,
            COALESCE(
                NULLIF(o.ИМЯ_В_ИМИН_ПАДЕЖЕ, ''),
                o.КОРОТКОЕ_ИМЯ
            )::TEXT AS ПОЛНЫЙ_ПУТЬ,
            ARRAY[o.ИД] AS ПОСЕЩЁННЫЕ
        FROM Н_ОТДЕЛЫ AS o
        WHERE o.ОТД_ИД IS NULL

        UNION ALL

        -- Рекурсивная часть: находим детей уже найденных подразделений
        SELECT
            child.ИД,
            child.ОТД_ИД,
            child.КОРОТКОЕ_ИМЯ,
            child.ИМЯ_В_ИМИН_ПАДЕЖЕ,
            parent.ГЛУБИНА + 1,
            parent.ПОЛНЫЙ_ПУТЬ || ' -> ' ||
                COALESCE(
                    NULLIF(child.ИМЯ_В_ИМИН_ПАДЕЖЕ, ''),
                    child.КОРОТКОЕ_ИМЯ
                ),
            parent.ПОСЕЩЁННЫЕ || child.ИД
        FROM Н_ОТДЕЛЫ AS child
        JOIN иерархия AS parent
            ON child.ОТД_ИД = parent.ИД
        WHERE NOT (child.ИД = ANY(parent.ПОСЕЩЁННЫЕ))
    )
    SELECT
        ИД,
        ОТД_ИД,
        КОРОТКОЕ_ИМЯ,
        ПОЛНЫЙ_ПУТЬ,
        ГЛУБИНА
    FROM иерархия
    ORDER BY ПОЛНЫЙ_ПУТЬ;

### Как читать запрос

1. Начальная часть выбирает подразделения без родителя и задаёт им глубину 0.
2. `UNION ALL` объединяет начальную выборку с рекурсивной частью.
3. Условие `child.ОТД_ИД = parent.ИД` находит детей каждого уже найденного подразделения.
4. `parent.ГЛУБИНА + 1` увеличивает глубину на каждом уровне.
5. `parent.ПОЛНЫЙ_ПУТЬ || ' -> ' || ...` дописывает название очередного подразделения к пути от корня.
6. Массив `ПОСЕЩЁННЫЕ` не позволяет повторно пройти один и тот же идентификатор на текущем пути, если данные содержат цикл.

### Проверка перед выполнением

Убедиться, что в таблице есть корневые строки:

    SELECT ИД, ОТД_ИД, КОРОТКОЕ_ИМЯ
    FROM Н_ОТДЕЛЫ
    WHERE ОТД_ИД IS NULL;

Проверить внешний ключ столбца `ОТД_ИД`:

    SELECT conname, pg_get_constraintdef(oid)
    FROM pg_constraint
    WHERE conrelid = 'н_отделы'::regclass
      AND contype = 'f';

Ожидается ограничение, связывающее `Н_ОТДЕЛЫ.ОТД_ИД` с `Н_ОТДЕЛЫ.ИД`. Если корневые строки не определяются через NULL, нужно выяснить по реальным данным, как обозначается верхний уровень. В учебном примере глубина корневого подразделения принята за 0.
