# Теория и вопросы к защите лабораторной работы № 3

**Предметная область:** герои, книги, островки и сбор ресурсов.  
**СУБД:** PostgreSQL.

Конспект включает темы из задания и ответы на все вопросы к защите. Примеры SQL ориентированы на PostgreSQL. Там, где важно различать общий теоретический термин и конкретную реализацию PostgreSQL, это отмечено отдельно.

## 1. Функциональные зависимости

### 1.1. Определение

Функциональная зависимость X → Y в отношении R означает, что любые две строки R, совпадающие по атрибутам X, обязательно совпадают и по атрибутам Y.

X называется детерминантом, Y — зависимой частью.

Пример из лабораторной:

    Герой(id_героя, имя, бодрствует)

    id_героя → имя
    id_героя → бодрствует

Если идентификаторы двух строк героя совпали, то имя и состояние бодрствования также должны совпасть. Поэтому id_героя определяет остальные атрибуты.

### 1.2. Виды функциональных зависимостей

**Тривиальная зависимость.** Y входит в X. Например, (A, B) → A. Такая зависимость выполняется по определению.

**Нетривиальная зависимость.** Y не является подмножеством X. Например, id_героя → имя.

**Полная функциональная зависимость.** Y функционально зависит от всего составного детерминанта X, но не зависит от любого его собственного подмножества.

Пример: (id_заказа, номер_строки) → количество, если ни один из этих атрибутов по отдельности не определяет количество.

**Частичная функциональная зависимость.** Неключевой атрибут зависит от собственного подмножества составного кандидатного ключа. Это нарушение 2NF.

Например, если ключ — (id_заказа, id_товара), но id_товара → название_товара, то название товара зависит только от части составного ключа.

**Транзитивная зависимость.** Возникает, когда X → Y и Y → Z, поэтому X → Z. Для нарушения 3NF важна транзитивная зависимость неключевого атрибута через другой неключевой атрибут.

Пример:

    id_сотрудника → id_отдела
    id_отдела → название_отдела

Следовательно, id_сотрудника → название_отдела. Обычно название отдела следует хранить в отдельном отношении «Отдел».

### 1.3. Суперключ, кандидатный ключ и простой атрибут

**Суперключ** — множество атрибутов, однозначно определяющее все атрибуты отношения.

**Кандидатный ключ** — минимальный суперключ: если удалить из него любой атрибут, свойство суперключа потеряется.

**Первичный ключ** — один из кандидатных ключей, выбранный как основной.

**Простой (prime) атрибут** — атрибут, входящий хотя бы в один кандидатный ключ. **Непростой (non-prime)** — не входящий ни в один кандидатный ключ.

Нормальные формы определяются относительно всех кандидатных ключей, а не только относительно выбранного PRIMARY KEY.

### 1.4. Замыкание атрибутов

Замыкание X+, или closure, — множество всех атрибутов, которые функционально определяются X при заданном множестве зависимостей F.

Для отношения «Герой»:

    F = {
        id_героя → имя,
        id_героя → бодрствует
    }

Получаем:

    id_героя+ = {id_героя, имя, бодрствует}

Поскольку в замыкание вошли все атрибуты отношения, id_героя — суперключ.

Замыкание удобно использовать для поиска кандидатных ключей и проверки того, следует ли одна функциональная зависимость из других.

## 2. Нормализация и нормальные формы

Нормализация — последовательная организация отношений для уменьшения избыточности и аномалий вставки, обновления и удаления.

### 2.1. Первая нормальная форма — 1NF

Отношение находится в 1NF, если атрибуты содержат атомарные значения в рамках выбранной модели данных и нет повторяющихся групп.

Плохой пример: в одном поле хранится строка «моллюски, устрицы, рыба» как список видов добычи, хотя с каждым видом требуется работать отдельно.

Лучше представить каждый вид отдельной строкой или отдельным отношением.

Атомарность зависит от предметной области: телефонный номер может считаться одним значением, даже если в нём есть код страны и разделители.

### 2.2. Вторая нормальная форма — 2NF

Отношение находится в 2NF, если:

1. оно находится в 1NF;
2. каждый неключевой атрибут полностью функционально зависит от каждого кандидатного ключа.

Иными словами, не должно быть зависимости неключевого атрибута от собственного подмножества составного кандидатного ключа.

Пример нарушения:

    ЗаказТовар(id_заказа, id_товара, название_товара, количество)
    PK = (id_заказа, id_товара)

При этом:

    (id_заказа, id_товара) → количество
    id_товара → название_товара

Название товара зависит только от части составного ключа — id_товара. Поэтому отношение не находится в 2NF.

Разложение:

    Товар(id_товара, название_товара)
    СтрокаЗаказа(id_заказа, id_товара, количество)

### 2.3. Третья нормальная форма — 3NF

Формальное определение: отношение находится в 3NF, если для каждой нетривиальной зависимости X → A верно хотя бы одно:

- X — суперключ;
- A — простой атрибут, то есть входит хотя бы в один кандидатный ключ.

Упрощённое учебное объяснение: неключевые атрибуты должны зависеть от ключа, всего ключа и ничего, кроме ключа; неключевой атрибут не должен транзитивно определяться через другой неключевой атрибут.

Формальное определение с простыми атрибутами точнее. Оно важно для отношений, в которых есть несколько кандидатных ключей.

### 2.4. Нормальная форма Бойса — Кодда (BCNF)

Отношение находится в BCNF, если для каждой нетривиальной функциональной зависимости X → Y детерминант X является суперключом.

BCNF строже 3NF: в 3NF допускается исключение, когда правая часть — простой атрибут; в BCNF такого исключения нет.

Пример отношения, которое находится в 3NF, но не в BCNF:

    Преподавание(студент, преподаватель, курс)

Предположим, что:

    преподаватель → курс
    (студент, курс) → преподаватель

Кандидатные ключи:

    (студент, преподаватель)
    (студент, курс)

Все три атрибута являются простыми, поскольку каждый входит хотя бы в один кандидатный ключ.

Зависимость преподаватель → курс нарушает BCNF: преподаватель не является суперключом. Но в 3NF она допустима, потому что курс — простой атрибут.

### 2.5. Четвёртая нормальная форма — 4NF

4NF устраняет нежелательные многозначные зависимости.

Многозначная зависимость X ↠ Y означает, что для одного X существует множество значений Y, независимое от остальных атрибутов отношения.

Условие 4NF: для каждой нетривиальной многозначной зависимости X ↠ Y детерминант X должен быть суперключом.

Пример: у человека независимо друг от друга есть языки и хобби.

    Человек(человек, язык, хобби)

Если у Алисы языки {русский, английский}, а хобби {шахматы, плавание}, в отношении получаются все сочетания языков и хобби. Это дублирование независимых наборов.

Разложение:

    ЯзыкЧеловека(человек, язык)
    ХоббиЧеловека(человек, хобби)

Так сохраняются два независимых факта без декартова размножения строк.

### 2.6. Пятая нормальная форма — 5NF

5NF также называют проекционно-соединительной нормальной формой.

Отношение находится в 5NF, если каждая нетривиальная зависимость соединения (join dependency), которая его характеризует, следует из кандидатных ключей. Иначе говоря, нельзя без потери смысла разложить отношение на более простые отношения и затем соединить их обратно, получив ложные сочетания.

Классический пример — отношение поставок:

    Поставка(поставщик, деталь, проект)

В зависимости от бизнес-правил факт поставки может определяться сочетанием нескольких бинарных отношений: поставщик—деталь, поставщик—проект, деталь—проект. Такое разложение корректно только если исходная тройная связь действительно восстанавливается из этих проекций без ложных строк.

Ключевой риск — при JOIN могут появиться комбинации, которых в исходном отношении не было. Поэтому декомпозиция должна быть lossless (без потерь) и соответствовать реальной семантике.

### 2.7. Шестая нормальная форма — 6NF

Отношение находится в 6NF, если оно не имеет нетривиальных зависимостей соединения: его нельзя дальше разложить на проекции без потери информации, кроме тривиальных разложений.

6NF особенно полезна в темпоральных БД, когда разные факты об одном объекте имеют независимые интервалы действия.

Например, зарплата сотрудника менялась с одних дат, а отдел — с других. Если хранить всё в одной большой таблице, независимые периоды могут порождать множество повторяющихся сочетаний. Можно хранить отдельные темпоральные отношения:

    ЗарплатаСотрудника(id_сотрудника, зарплата, период)
    ОтделСотрудника(id_сотрудника, id_отдела, период)

Это уменьшает смешивание независимых временных фактов, но увеличивает число JOIN.

### 2.8. Сравнение нормальных форм

| Форма | Что устраняет или ограничивает |
|---|---|
| 1NF | Повторяющиеся группы и неатомарные значения в выбранной модели |
| 2NF | Частичные зависимости неключевых атрибутов от кандидатных ключей |
| 3NF | Транзитивные зависимости неключевых атрибутов и более общий критерий ФЗ |
| BCNF | Любую нетривиальную ФЗ с детерминантом, не являющимся суперключом |
| 4NF | Нетривиальные многозначные зависимости с несуперключевым детерминантом |
| 5NF | Нетривиальные зависимости соединения, не следующие из ключей |
| 6NF | Все нетривиальные зависимости соединения |

Для обычной учебной схемы часто достаточно проверить 1NF–BCNF. 4NF и 5NF важны, когда модель содержит независимые многозначные факты или нетривиальные зависимости соединения. 6NF чаще встречается в специальных, в частности темпоральных, моделях.

## 3. Денормализация

Денормализация — осознанное введение избыточности или хранение заранее вычисленных значений ради ускорения чтения и снижения стоимости запросов.

Она не означает автоматически ошибку проектирования. Важно, чтобы выигрыш в производительности был обоснован, а согласованность дублируемых данных поддерживалась явно.

### 3.1. Типичные способы

- Дублирование атрибута из связанной таблицы.
- Хранение предварительно вычисленного агрегата: суммы, количества, среднего значения.
- Хранение булевого признака, который можно вывести из наличия связанной записи.
- Материализованное представление с сохранённым результатом запроса.
- Хранение иерархического пути или идентификатора родителя/предка для ускорения выборок.

### 3.2. Плюсы и минусы

| Плюсы | Минусы |
|---|---|
| Меньше JOIN и вычислений при чтении | Нужно обновлять копии данных |
| Быстрее частые отчётные запросы | Риск рассинхронизации |
| Можно использовать специализированные индексы | Сложнее INSERT, UPDATE и DELETE |
| Упрощается получение часто используемых показателей | Требуется тестирование всех путей изменения данных |

### 3.3. Денормализация в лабораторной

В таблицу «Добыча» добавлено поле собрана.

Его можно вычислить по наличию записи в «Состав_собирания», но отдельный BOOLEAN позволяет фильтровать свободные ресурсы без дополнительного соединения.

Для согласованности создан триггер:

- INSERT в «Состав_собирания» устанавливает собрана = TRUE;
- DELETE из «Состав_собирания» возвращает собрана = FALSE и меняет координаты ресурса.

Второе предложение — добавить id_островка в «Добыча» — в тексте отчёта описано как полезная денормализация, но в итоговом DDL не реализовано.

## 4. Функциональные зависимости и аксиомы Армстронга

### 4.1. Аксиомы

Аксиомы Армстронга — три правила вывода функциональных зависимостей.

**1. Рефлексивность.** Если Y ⊆ X, то X → Y.

Пример: (A, B) → A.

**2. Пополнение (augmentation).** Если X → Y, то XZ → YZ для любого Z.

Пример: если A → B, то AC → BC.

**3. Транзитивность.** Если X → Y и Y → Z, то X → Z.

Пример: A → B и B → C означают A → C.

Эти аксиомы корректны и полны для вывода функциональных зависимостей: из них можно вывести все зависимости, логически следующие из данного множества ФЗ.

### 4.2. Полезные производные правила

**Декомпозиция:** из X → YZ следует X → Y и X → Z.

**Объединение:** из X → Y и X → Z следует X → YZ.

**Псевдотранзитивность:** из X → Y и WY → Z следует WX → Z.

**Композиция:** из X → Y и Z → W следует XZ → YW.

### 4.3. Пример для своей схемы

Для «Героя»:

    id_героя → имя
    id_героя → бодрствует

По объединению:

    id_героя → {имя, бодрствует}

Замыкание:

    id_героя+ = {id_героя, имя, бодрствует}

Поскольку замыкание содержит все атрибуты, id_героя является суперключом.

## 5. PL/pgSQL: функции, блоки и триггеры

### 5.1. Что такое PL/pgSQL

PL/pgSQL — процедурный язык PostgreSQL, который расширяет SQL переменными, условиями, циклами, обработкой исключений и возможностью создавать функции и триггерные функции.

Обычный SQL описывает, какие данные нужно получить или изменить. PL/pgSQL позволяет описать последовательность действий, ветвления и проверки.

### 5.2. Структура блока

```sql
DECLARE
    v_count INTEGER;
BEGIN
    SELECT COUNT(*)
    INTO v_count
    FROM добыча
    WHERE собрана = FALSE;

    IF v_count = 0 THEN
        RAISE NOTICE 'Свободной добычи нет';
    END IF;
END;
```

- DECLARE — объявление локальных переменных; блок может обходиться без него.
- BEGIN — начало исполняемой части PL/pgSQL-блока.
- IF / LOOP / FOR / WHILE — управление выполнением.
- END — завершение блока, а не фиксация транзакции.
- RAISE — сообщение, предупреждение или исключение.

### 5.3. Функция и процедура

**Функция** вызывается в SQL-выражении через SELECT, в выражении или в другом SQL-операторе и возвращает значение (в том числе строку, таблицу или void). Функции не могут выполнять COMMIT или ROLLBACK текущей транзакции.

**Процедура** вызывается командой CALL. В PostgreSQL процедуры, запущенные на верхнем уровне через CALL, при соблюдении ограничений могут управлять границами транзакций с помощью COMMIT и ROLLBACK.

### 5.4. Триггер и триггерная функция

Триггер автоматически запускает функцию в ответ на событие в таблице или представлении.

Типы по времени:

- BEFORE — до изменения строки;
- AFTER — после изменения строки;
- INSTEAD OF — вместо изменения строки, обычно для представления.

Уровень:

- FOR EACH ROW — один вызов на каждую затронутую строку;
- FOR EACH STATEMENT — один вызов на SQL-команду.

У триггерной функции есть специальные переменные:

| Переменная | Значение |
|---|---|
| TG_OP | Операция: INSERT, UPDATE, DELETE или TRUNCATE |
| NEW | Новая строка для INSERT/UPDATE |
| OLD | Старая строка для UPDATE/DELETE |
| TG_TABLE_NAME | Имя таблицы |
| TG_WHEN | BEFORE или AFTER |
| TG_LEVEL | ROW или STATEMENT |
| FOUND | Результат последней подходящей SQL-операции в PL/pgSQL |

В строковом триггере после INSERT/UPDATE обычно возвращают NEW, после DELETE — OLD. Для AFTER-триггеров возвращаемое значение игнорируется, но RETURN NEW/OLD остаётся привычным шаблоном.

В лабораторной реализованы триггеры синхронизации добычи, ручного сбора и автоматического сбора при перемещении героя.

# Ответы на вопросы к защите

## 6. В строке заказа хранится цена товара. Это денормализация?

**Не обязательно. Чаще это правильное хранение исторического факта, а не избыточное копирование.**

Нужно различать две цены:

- текущая цена товара в каталоге;
- цена, по которой товар действительно продали в конкретном заказе.

Пример:

```sql
CREATE TABLE товар (
    id_товара BIGINT PRIMARY KEY,
    название TEXT NOT NULL,
    текущая_цена NUMERIC(12, 2) NOT NULL
);

CREATE TABLE строка_заказа (
    id_заказа BIGINT NOT NULL,
    id_товара BIGINT NOT NULL REFERENCES товар(id_товара),
    количество INTEGER NOT NULL,
    цена_на_момент_заказа NUMERIC(12, 2) NOT NULL,
    PRIMARY KEY (id_заказа, id_товара)
);
```

Допустим, товар стоил 1000 рублей в день заказа. Через неделю цена в каталоге изменилась на 1200 рублей. Исторический заказ всё равно должен показывать сумму по цене 1000 рублей.

Поэтому поле цена_на_момент_заказа — самостоятельный факт строки заказа. Это не просто копия текущей цены. Оно фиксирует коммерческие условия конкретной сделки.

**Когда это было бы денормализацией?** Если в строке заказа хранить копию текущей цены товара, которая всегда обязана полностью совпадать с товар.текущая_цена, и это значение можно без потери смысла получать JOIN-ом. Тогда появляется дублирование, которое нужно синхронизировать.

**Ответ преподавателю:** цена в строке заказа сама по себе не означает денормализацию. Историческая цена — атрибут факта продажи. Денормализация возникает, когда копируется значение, которое должно совпадать с текущим значением в другой таблице.

## 7. Чем BEGIN ... END в PL/pgSQL отличается от BEGIN и COMMIT в SQL? Можно ли начать новую транзакцию внутри функции? А завершить текущую?

Здесь одинаковые слова имеют разный смысл.

### BEGIN и END в PL/pgSQL

Внутри тела функции это обозначение блока:

```sql
CREATE FUNCTION пример()
RETURNS INTEGER
LANGUAGE plpgsql
AS $$
DECLARE
    v_value INTEGER := 10;
BEGIN
    v_value := v_value + 5;
    RETURN v_value;
END;
$$;
```

BEGIN начинает исполняемую часть блока, END закрывает её. Они не открывают и не фиксируют транзакцию.

### BEGIN и COMMIT в SQL

На уровне SQL:

```sql
BEGIN;

UPDATE добыча
SET собрана = TRUE
WHERE id_добычи = 1;

COMMIT;
```

- BEGIN начинает транзакцию;
- COMMIT фиксирует изменения;
- ROLLBACK отменяет изменения текущей незавершённой транзакции.

### Можно ли управлять транзакциями из функции?

Обычная функция PostgreSQL не может самостоятельно начать, зафиксировать или отменить транзакцию. Вызов функции выполняется внутри транзакции вызывающего SQL-оператора.

Поэтому внутри функции нельзя использовать COMMIT или ROLLBACK для завершения внешней транзакции.

### А из процедуры?

Процедуры, вызванные через CALL, и анонимные блоки DO могут выполнять COMMIT и ROLLBACK, но только при соблюдении ограничений: вызов должен происходить на верхнем уровне либо в допустимой цепочке CALL/DO без промежуточного SELECT или другого оператора, запрещающего управление транзакцией.

После COMMIT или ROLLBACK PostgreSQL автоматически начинает новую транзакцию. Отдельный BEGIN для её старта не нужен.

Нельзя завершать транзакцию внутри блока с обработчиком EXCEPTION: такой блок работает как подпараметрическая транзакция.

**Ответ преподавателю:** BEGIN/END в PL/pgSQL обозначают границы процедурного блока. BEGIN/COMMIT в SQL управляют транзакцией. Функция не может завершить внешнюю транзакцию; процедура при вызове через CALL может управлять транзакциями в разрешённом контексте.

## 8. Отношение с простым первичным ключом всегда находится во 2НФ?

**Если у отношения все кандидатные ключи простые, то да. Но один лишь простой первичный ключ не гарантирует 2NF.**

Почему обычно отвечают «да»: частичная зависимость возможна только от собственного подмножества составного ключа. У простого ключа нет собственного непустого подмножества, поэтому частичная зависимость от части этого ключа невозможна.

Но нормальные формы проверяются по всем кандидатным ключам, а не только по выбранному первичному.

Рассмотрим отношение:

    R(A, B, C, D)

Функциональные зависимости:

    A → B, C, D
    B C → A
    B → D

Кандидатные ключи:

    A
    (B, C)

Первичным ключом выберем A — он простой. Но у отношения есть и составной кандидатный ключ (B, C).

Зависимость:

    B → D

нарушает 2NF: B — собственное подмножество составного кандидатного ключа (B, C), а D — неключевой атрибут, поскольку не входит ни в один кандидатный ключ.

Следовательно, отношение не находится в 2NF, хотя выбранный первичный ключ A простой.

**Точная формулировка:** если все кандидатные ключи отношения состоят из одного атрибута, то при условии 1NF отношение автоматически находится в 2NF. Если простой только первичный ключ, но имеются другие составные кандидатные ключи, нужно проверять их отдельно.

## 9. Нормальные формы: 1NF, 2NF, 3NF, BCNF, 4NF, 5NF, 6NF

Развёрнутые определения, условия и примеры приведены в разделе 2 этого конспекта.

Для устного ответа:

- 1NF — атомарные значения и отсутствие повторяющихся групп.
- 2NF — отсутствие частичных зависимостей неключевых атрибутов от кандидатных ключей.
- 3NF — для каждой нетривиальной ФЗ детерминант является суперключом либо правая часть — простой атрибут.
- BCNF — детерминант каждой нетривиальной ФЗ обязательно суперключ.
- 4NF — отсутствие нетривиальных многозначных зависимостей с несуперключевым детерминантом.
- 5NF — отсутствие нетривиальных зависимостей соединения, не следующих из кандидатных ключей.
- 6NF — отсутствие нетривиальных зависимостей соединения; отношение далее не разлагается без потери информации.

Главное различие: 2NF–BCNF работают с функциональными зависимостями, 4NF — с многозначными, 5NF и 6NF — с зависимостями соединения.

## 10. Сформулируйте аксиомы Армстронга

1. **Рефлексивность:** если Y ⊆ X, то X → Y.
2. **Пополнение:** если X → Y, то XZ → YZ.
3. **Транзитивность:** если X → Y и Y → Z, то X → Z.

Из них выводятся полезные правила:

- декомпозиция: X → YZ ⇒ X → Y и X → Z;
- объединение: X → Y и X → Z ⇒ X → YZ;
- псевдотранзитивность: X → Y и WY → Z ⇒ WX → Z.

Аксиомы используются для вывода зависимостей, вычисления замыканий, проверки ключей и минимального покрытия ФЗ.

Пример для своей таблицы «Герой»:

    id_героя → имя
    id_героя → бодрствует

По объединению получаем:

    id_героя → {имя, бодрствует}

## 11. Пример триггера, который можно заменить на RLS / составной FK

Это два разных механизма: RLS заменяет проверки доступа к строкам, а составной внешний ключ заменяет проверки ссылочной целостности по нескольким столбцам.

### 11.1. Триггер, который проверяет доступ владельца к строке: вместо него подходит RLS

Предположим, есть таблица документов с owner_id. Триггер до SELECT/UPDATE/DELETE проверяет, что текущий пользователь является владельцем документа.

Для ограничения доступа к строкам лучше использовать Row-Level Security (RLS):

```sql
ALTER TABLE документы ENABLE ROW LEVEL SECURITY;

CREATE POLICY документы_только_свои
ON документы
USING (
    owner_id = NULLIF(
        current_setting('app.user_id', true),
        ''
    )::BIGINT
)
WITH CHECK (
    owner_id = NULLIF(
        current_setting('app.user_id', true),
        ''
    )::BIGINT
);
```

- USING определяет, какие уже существующие строки пользователь может видеть или изменять.
- WITH CHECK проверяет новые значения строк при INSERT и UPDATE.
- При включённом RLS отсутствие подходящей политики означает запрет по умолчанию.
- RLS применяется к SELECT, INSERT, UPDATE и DELETE с учётом конкретной политики.

Важное замечание по безопасности: пользовательское GUC app.user_id должно задаваться доверенным приложением и не должно без проверки приниматься как достоверная идентичность при прямом доступе клиента к БД. Для реальной системы безопаснее связывать доступ с надёжно установленной ролью или контекстом с контролируемыми правами.

### 11.2. Триггер, который проверяет соответствие пары ключей: вместо него подходит составной FK

Предположим, товар принадлежит продавцу. Триггер на строке заказа проверяет, что указанный товар действительно принадлежит указанному продавцу.

Вместо триггера можно выразить правило составным внешним ключом:

```sql
CREATE TABLE товар_продавца (
    id_продавца BIGINT NOT NULL,
    id_товара BIGINT NOT NULL,
    PRIMARY KEY (id_продавца, id_товара)
);

CREATE TABLE строка_заказа (
    id_строки BIGINT PRIMARY KEY,
    id_продавца BIGINT NOT NULL,
    id_товара BIGINT NOT NULL,
    количество INTEGER NOT NULL,
    FOREIGN KEY (id_продавца, id_товара)
        REFERENCES товар_продавца(id_продавца, id_товара)
);
```

Пара (id_продавца, id_товара) обязана существовать в родительской таблице. Составной FK гарантирует, что товар связан именно с этим продавцом.

### 11.3. Когда эти механизмы не подходят

- RLS не предназначен для реализации произвольных бизнес-операций, например автоматического списания ресурса или создания истории события.
- Составной FK проверяет существование соответствующей пары ключей. Он не выполняет сложные вычисления и не заменяет произвольную логику.
- Триггер остаётся уместным, когда нужно изменить другие данные, вычислить значения, создать связанную запись или реализовать правило, которое нельзя выразить декларативным ограничением.

В собственной лабораторной функции ручного сбора и автоматического сбора при перемещении героя обычный FK или RLS не заменят триггерную логику: она выбирает ресурсы по расстоянию, создаёт события и меняет состояние добычи.

## 12. Какие направления есть у FETCH и MOVE?

Обе команды работают с курсором. Курсор хранит позицию в результате запроса.

**FETCH** перемещает позицию курсора и возвращает строки.  
**MOVE** перемещает позицию курсора, но строки не возвращает.

Основные направления:

| Направление | Значение |
|---|---|
| NEXT | Следующая строка; значение по умолчанию |
| PRIOR | Предыдущая строка |
| FIRST | Первая строка |
| LAST | Последняя строка |
| ABSOLUTE n | Перейти к строке с номером n; отрицательное n считает с конца |
| RELATIVE n | Перейти относительно текущей позиции; отрицательное значение — назад |
| FORWARD | Вперёд на одну строку |
| FORWARD n | Вперёд на n строк |
| FORWARD ALL | Все оставшиеся строки вперёд |
| BACKWARD | Назад на одну строку |
| BACKWARD n | Назад на n строк |
| BACKWARD ALL | Все предыдущие строки назад |

Число без слова FORWARD означает выбор следующего указанного количества строк. ALL эквивалентен FORWARD ALL.

Пример:

```sql
BEGIN;

DECLARE курсор_ресурсов SCROLL CURSOR FOR
SELECT id_добычи, вид_добычи
FROM добыча
ORDER BY id_добычи;

FETCH NEXT FROM курсор_ресурсов;
FETCH PRIOR FROM курсор_ресурсов;
FETCH ABSOLUTE 3 FROM курсор_ресурсов;

MOVE FORWARD 5 FROM курсор_ресурсов;
FETCH NEXT FROM курсор_ресурсов;

CLOSE курсор_ресурсов;
COMMIT;
```

SCROLL разрешает движение в обратном направлении и произвольное перемещение по результату. Если курсор объявлен как NO SCROLL, произвольное движение назад не поддерживается.

Ключевое отличие: FETCH показывает строки, MOVE только меняет положение курсора и возвращает количество перемещённых строк в командном статусе.

## 13. Что такое расширенная реляционная алгебра мультимножеств? Какие операции добавлены и зачем?

### 13.1. Множество и мультимножество

Классическая реляционная алгебра рассматривает отношение как множество кортежей: одинаковая строка не может встречаться несколько раз.

В SQL по умолчанию часто используется мультимножественная семантика (bag semantics): одинаковые строки могут повторяться.

Пример:

```sql
SELECT имя FROM студент
UNION ALL
SELECT имя FROM преподаватель;
```

Если одно имя есть в обеих таблицах, оно останется в результате дважды. Обычный UNION, наоборот, удаляет дубликаты.

Удобно описывать мультимножество функцией кратности m_R(t): она показывает, сколько раз кортеж t встречается в отношении R.

### 13.2. Операции мультимножеств

**Выборка σ.** Оставляет строки, для которых предикат истинен. Кратность подходящей строки сохраняется.

**Проекция π.** Оставляет выбранные атрибуты. Если разные исходные строки после проекции становятся одинаковыми, их кратности суммируются в мультимножественной алгебре. Для удаления повторов отдельно применяется DISTINCT.

**Объединение.** В мультимножественной семантике кратности складываются:

    m_(R UNION ALL S)(t) = m_R(t) + m_S(t)

**Пересечение ALL.** Кратность результата равна меньшей кратности:

    m_(R INTERSECT ALL S)(t) = min(m_R(t), m_S(t))

**Разность ALL.** Из кратности левого отношения вычитается кратность правого, отрицательный результат заменяется нулём:

    m_(R EXCEPT ALL S)(t) = max(0, m_R(t) - m_S(t))

**Декартово произведение.** Кратности комбинаций строк перемножаются.

**Соединение.** Комбинирует подходящие строки двух отношений. Обычно можно представить как выборку над декартовым произведением.

### 13.3. Операции расширенной реляционной алгебры

Во многих курсах к базовым операциям дополнительно относят:

- расширенную проекцию — вычисляемые атрибуты и выражения;
- группировку и агрегирование — γ, COUNT, SUM, AVG, MIN, MAX;
- внешние соединения — LEFT, RIGHT, FULL OUTER JOIN;
- полусоединение — возвращает строки одной стороны, для которых найдена пара на другой;
- антисоединение — возвращает строки, для которых пары нет.

Точный состав операций расширенной алгебры зависит от учебника. Вопрос про мультимножества дополнительно подчёркивает не только наличие агрегатов и соединений, но и сохранение кратности строк.

### 13.4. Зачем это нужно

SQL проектировался для практических запросов к БД, где повторы могут иметь значение. Например, если две независимые таблицы содержат по строке с одинаковым именем, после UNION ALL в результате должны сохраниться обе записи.

Мультимножественная модель позволяет:

- не выполнять удаление дубликатов после каждой операции;
- корректно моделировать SQL UNION ALL, INTERSECT ALL и EXCEPT ALL;
- правильно описывать кратность строк после JOIN и PROJECT;
- понимать, почему COUNT(*) считает повторяющиеся строки.

В SQL DISTINCT явно удаляет повторы, а операции UNION, INTERSECT и EXCEPT без ALL обычно применяют семантику с удалением дубликатов.

## 14. Кешируется ли план у команды EXECUTE?

Вопрос неоднозначен: в PostgreSQL есть SQL-команда EXECUTE для ранее подготовленного оператора PREPARE и отдельный оператор EXECUTE внутри PL/pgSQL для динамического SQL. Их нельзя смешивать.

### 14.1. SQL PREPARE и EXECUTE

```sql
PREPARE поиск_добычи(BIGINT) AS
SELECT *
FROM добыча
WHERE id_добычи = $1;

EXECUTE поиск_добычи(10);
EXECUTE поиск_добычи(20);
```

PREPARE создаёт серверный подготовленный оператор. PostgreSQL сохраняет его в пределах сессии, чтобы не повторять полный цикл разбора и анализа запроса.

При выполнении возможны два вида плана:

- **Custom plan** — строится с учётом фактических значений параметров конкретного вызова.
- **Generic plan** — общий план, повторно используемый для разных значений параметров.

При plan_cache_mode = auto PostgreSQL сначала выполняет первые пять вызовов параметризованного подготовленного оператора с custom plans, оценивает их среднюю стоимость, затем сравнивает её с оценкой generic plan. В последующих вызовах выбирается более выгодный вариант по внутренней эвристике.

Посмотреть используемый план:

```sql
EXPLAIN EXECUTE поиск_добычи(10);
```

Если в плане указаны конкретные значения — используется custom plan. Если остаются параметры вида $1 — generic plan.

### 14.2. EXECUTE внутри PL/pgSQL

```sql
EXECUTE
    'SELECT COUNT(*) FROM добыча WHERE вид_добычи = $1'
INTO v_count
USING v_kind;
```

Динамический EXECUTE в PL/pgSQL **перепланирует команду при каждом выполнении**. Это полезно, когда текст запроса или значения параметров сильно меняют оптимальный план. В отличие от обычной статической SQL-команды в PL/pgSQL, динамический EXECUTE не использует сохранённый план для повторного выполнения этой команды.

Обычные статические SQL-команды внутри PL/pgSQL могут использовать кеширование планов; PostgreSQL может выбирать generic plan или строить custom plan в зависимости от ситуации.

### 14.3. Итоговый ответ

Если речь о SQL EXECUTE подготовленного оператора PREPARE — оператор и план могут кешироваться и переиспользоваться, но план может быть generic или custom и может быть перепланирован.

Если речь о динамическом EXECUTE в PL/pgSQL — команда планируется заново при каждом выполнении.

## 15. Почему в PostgreSQL нет CREATE ASSERTION из стандарта SQL и чем это заменяют?

### 15.1. Что такое ASSERTION

В стандарте SQL ASSERTION — ограничение целостности уровня всей схемы. Оно может выражать условие, зависящее от нескольких таблиц и множества строк, а не только от одной строки конкретной таблицы.

Пример условного бизнес-правила: сумма резервов по всем счетам клиента не должна превышать лимит клиента.

Это сложнее, чем обычный CHECK: изменение в одной таблице может нарушить условие, определяемое данными нескольких других таблиц.

**PostgreSQL не реализует CREATE ASSERTION.** Поэтому нельзя создать единственное декларативное ASSERTION, которое автоматически проверяет произвольное условие над несколькими таблицами.

Не следует выдавать отсутствие команды за отсутствие механизмов контроля целостности: в PostgreSQL есть более узкие типы ограничений и пользовательские триггеры.

### 15.2. Чем заменяют

Выбирать нужно самый декларативный и точный механизм, который выражает бизнес-правило:

| Задача | Подходящий механизм |
|---|---|
| Запрет NULL | NOT NULL |
| Проверка значения в строке | CHECK |
| Уникальность строки или пары значений | UNIQUE |
| Существование родительской записи | FOREIGN KEY |
| Ограничение на пересечение диапазонов/геометрии | EXCLUDE, если правило можно выразить операторами |
| Сложное правило между несколькими строками или таблицами | Триггер |
| Проверка в конце транзакции | DEFERRABLE constraint trigger |

### 15.3. Почему CHECK не заменяет ASSERTION

PostgreSQL не рекомендует использовать CHECK для проверки других строк или таблиц. CHECK должен проверять значения текущей строки, а не состояние всей БД. Иначе изменение другой строки может сделать ранее выполненный CHECK ложным, не запустив его повторно; возможны проблемы и при восстановлении из дампа.

### 15.4. Пример замены через constraint trigger

Когда правило действительно нельзя выразить FK, UNIQUE или CHECK, можно использовать constraint trigger:

```sql
CREATE CONSTRAINT TRIGGER проверка_лимита
AFTER INSERT OR UPDATE OR DELETE
ON резерв
DEFERRABLE INITIALLY DEFERRED
FOR EACH ROW
EXECUTE FUNCTION проверить_лимит_резервов();
```

Это только форма объявления триггера. Функция проверить_лимит_резервов должна пересчитывать соответствующий агрегат и выбрасывать исключение, если лимит нарушен.

Отложенный триггер позволит проверять итоговое состояние транзакции, а не каждый промежуточный шаг. Но функцию необходимо проектировать с учётом конкурентных транзакций: простой SELECT/COUNT в триггере не всегда гарантирует отсутствие гонки при одновременных изменениях. Иногда нужны блокировки, отдельная таблица счётчиков, уникальные/исключающие ограничения или более строгая изоляция.

### 15.5. Итоговый ответ

PostgreSQL не поддерживает CREATE ASSERTION. Для локальных правил нужно применять NOT NULL, CHECK, UNIQUE, FOREIGN KEY и EXCLUDE; для сложных межстрочных и межтабличных правил — триггеры, в том числе отложенные constraint triggers. CHECK не предназначен для проверки произвольных данных в других строках или таблицах.

## 16. Что сообщают серверу COST и ROWS, а что — LEAKPROOF?

Это атрибуты функции из CREATE FUNCTION. Они влияют на оптимизатор и безопасность, но не меняют возвращаемое значение сами по себе.

### 16.1. COST

COST — оценка вычислительной стоимости вызова функции для планировщика PostgreSQL.

```sql
CREATE FUNCTION дорогая_проверка(p_id BIGINT)
RETURNS BOOLEAN
LANGUAGE plpgsql
COST 500
AS $$
BEGIN
    ...
END;
$$;
```

Стоимость выражается в условных единицах относительно cpu_operator_cost. Если COST выше, планировщик старается избегать лишних вызовов функции и может предпочитать план, в котором её вызовы происходят реже.

Значение COST — оценка, а не ограничение времени или реальное измерение. Если COST не указать, PostgreSQL использует 1 для функций на C и внутренних функций, а для функций на остальных языках — 100. Для set-returning function стоимость трактуется как стоимость на возвращаемую строку.

### 16.2. ROWS

ROWS — оценка количества строк, которое вернёт set-returning function.

```sql
CREATE FUNCTION свободная_добыча()
RETURNS SETOF добыча
LANGUAGE sql
ROWS 50
AS $$
    SELECT *
    FROM добыча
    WHERE собрана = FALSE;
$$;
```

По умолчанию планировщик предполагает 1000 строк. ROWS позволяет сообщить более реалистичную оценку, чтобы оптимизатор корректнее выбирал порядок JOIN и другие операции.

ROWS разрешён только для функций, возвращающих набор строк.

### 16.3. LEAKPROOF

LEAKPROOF — заявление разработчика, что функция не раскрывает информацию о своих аргументах иначе, чем через возвращаемое значение, и не имеет побочных эффектов.

Пример функции, которая не должна считаться leakproof:

- при некотором аргументе бросает исключение, в тексте которого содержит секретное значение;
- по-разному ведёт себя так, что пользователь может определить скрытые данные не через разрешённый результат функции.

Атрибут важен для RLS и security_barrier views. Оптимизатор может переставлять leakproof-функции относительно проверок безопасности, поскольку предполагается, что они не раскроют скрытые данные. Для обычных пользовательских функций LEAKPROOF может указывать только суперпользователь.

**Не ставить LEAKPROOF «для ускорения».** Это утверждение о безопасности функции, а не настройка производительности. Неверная маркировка может создать утечку информации.

### 16.4. Сводка

| Атрибут | Что сообщает | Для чего нужно |
|---|---|---|
| COST | Оценочную стоимость выполнения | Оценка выгодности плана |
| ROWS | Ожидаемое количество строк set-returning function | Оценка кардинальности при JOIN |
| LEAKPROOF | Функция не раскрывает аргументы через побочные эффекты или ошибки | Безопасный порядок выполнения относительно RLS/security barrier |

## 17. Почему внешние ключи в PostgreSQL реализованы триггерами, а не отдельным механизмом, и что из этого следует на практике?

### 17.1. Внешний ключ — всё равно ограничение

Когда объявляется:

```sql
FOREIGN KEY (id_героя)
REFERENCES герой(id_героя)
```

пользователь задаёт декларативное ограничение целостности. Оно хранится в системном каталоге pg_constraint как ограничение типа foreign key.

Внутри PostgreSQL проверки ссылочной целостности и действия ON DELETE/ON UPDATE выполняются специальными системными триггерными функциями. Это не пользовательские триггеры, которые разработчик вручную пишет через CREATE TRIGGER. В исходном коде PostgreSQL для этой логики есть файл ri_triggers.c — Referential Integrity Triggers.

### 17.2. Какие события нужно отслеживать

Внешний ключ должен реагировать на изменения в обеих сторонах связи:

| Операция | Проверка |
|---|---|
| INSERT в дочернюю таблицу | Существует ли родительская строка |
| UPDATE FK в дочерней таблице | Существует ли новая родительская строка |
| DELETE в родительской таблице | Не остались ли ссылающиеся дочерние строки |
| UPDATE ключа родителя | Не нарушаются ли существующие ссылки |

Триггерный механизм позволяет выполнять разные действия:

- NO ACTION — стандартная проверка ограничения;
- RESTRICT — запретить изменение/удаление при наличии зависимых строк;
- CASCADE — изменить или удалить зависимые строки;
- SET NULL — установить FK в NULL;
- SET DEFAULT — установить значение по умолчанию.

Также поддерживаются отложенные внешние ключи DEFERRABLE, когда проверка может произойти не сразу, а при завершении транзакции.

### 17.3. Практические следствия

**1. Не нужно писать собственный триггер для обычного FK.** Объявляем FOREIGN KEY, а PostgreSQL сам создаёт внутренние проверки и каскадные действия.

**2. Ограничение видно как FOREIGN KEY в системном каталоге.** Тип ограничения хранится в pg_constraint, даже несмотря на то, что выполнение обеспечивается внутренними триггерными функциями.

**3. Проверка затрагивает обе таблицы.** Поэтому изменение родительской строки может быть запрещено из-за существующей ссылки в дочерней таблице.

**4. FK можно сделать отложенным.** В сочетании с DEFERRABLE и SET CONSTRAINTS проверка может быть перенесена к концу транзакции.

**5. В дочерней таблице индекс автоматически не создаётся.** Для поиска родительских ключей индекс нужен и создаётся, когда объявляется PK/UNIQUE на родительской стороне. Но индекс на FK-столбцах дочерней таблицы PostgreSQL автоматически не добавляет. Его часто полезно создать для ускорения JOIN и проверок DELETE/UPDATE родителя.

Пример:

```sql
CREATE INDEX idx_перелистывание_по_книге
ON перелистывание(id_книги);
```

Такой индекс особенно полезен, если часто искать все строки связи для определённой книги или удалять/обновлять родительскую запись.

**6. Отключение триггеров может нарушить целостность.** Например, session_replication_role = replica подавляет обычное срабатывание триггеров и правил, включая механизм проверки внешних ключей. Это настройка для специальных сценариев репликации, а не обычный способ ускорить загрузку. Небрежное использование может оставить некорректные ссылки.

### 17.4. Почему такой механизм удобен

Ссылочная целостность — это реакция на операции над строками в обеих таблицах. Использование внутренней триггерной системы даёт единый способ обрабатывать проверки и referential actions, а также позволяет переиспользовать инфраструктуру отложенных ограничений.

Важна точная формулировка: внешний ключ не превращается в обычный пользовательский триггер. Это ограничение FOREIGN KEY, хранящееся в системном каталоге, реализация проверок которого использует специальные системные триггерные функции.

### 17.5. Итоговый ответ

Внешний ключ — декларативное ограничение PostgreSQL, а его проверки и действия каскада реализованы внутренними RI-триггерами. Это позволяет реагировать на INSERT/UPDATE дочерней таблицы и DELETE/UPDATE родительской, поддерживать CASCADE/RESTRICT/SET NULL/SET DEFAULT и отложенные проверки. На практике не надо создавать собственные триггеры для FK, но нужно помнить об индексах дочерних столбцов и осторожно обращаться с отключением триггеров.

## 18. Почему σθ∧φ(R) ≡ σθ(σφ(R))? Какие ещё законы для выборки вы знаете?

### 18.1. Почему равенство верно

σ — оператор выборки (selection): он оставляет строки, которые удовлетворяют предикату.

Выборка по условию θ ∧ φ оставит строку, только если одновременно истинны оба условия.

Последовательная выборка:

    σφ(R)

сначала оставляет строки, удовлетворяющие φ.

Затем:

    σθ(σφ(R))

из оставшихся строк убирает те, которые не удовлетворяют θ.

В результате остаются ровно те строки, для которых одновременно истинны θ и φ. Поэтому:

    σ_(θ ∧ φ)(R) = σ_θ(σ_φ(R))

Порядок можно поменять:

    σ_(θ ∧ φ)(R)
    = σ_θ(σ_φ(R))
    = σ_φ(σ_θ(R))

### 18.2. Законы выборки

**Каскад выборок:**

    σ_θ(σ_φ(R)) = σ_(θ ∧ φ)(R)

Несколько фильтров можно объединить в одно условие.

**Коммутативность:**

    σ_θ(σ_φ(R)) = σ_φ(σ_θ(R))

Порядок двух выборок не влияет на результат.

**Идемпотентность:**

    σ_θ(σ_θ(R)) = σ_θ(R)

Повторное применение того же условия ничего не меняет.

**Тождественная выборка:**

    σ_TRUE(R) = R

Условие, истинное для каждой строки, не изменяет отношение.

**Пустая выборка:**

    σ_FALSE(R) = ∅

Условие, ложное для каждой строки, даёт пустое отношение.

**Распределение по объединению:**

    σ_θ(R ∪ S) = σ_θ(R) ∪ σ_θ(S)

Можно отфильтровать части отдельно и затем объединить результаты.

**Распределение по разности:**

    σ_θ(R − S) = σ_θ(R) − σ_θ(S)

Это равенство для классической множественной реляционной алгебры.

**Проталкивание выборки через декартово произведение:**

Если θ использует только атрибуты R, то:

    σ_θ(R × S) = σ_θ(R) × S

Фильтровать R можно до построения произведения, тем самым уменьшая промежуточный результат.

**Проталкивание выборки через JOIN:**

Если θ использует только атрибуты R:

    σ_θ(R ⋈_φ S) = σ_θ(R) ⋈_φ S

Так условие можно выполнить на одной стороне соединения до JOIN.

### 18.3. Зачем эти законы нужны

Законы используются для эквивалентных преобразований запросов и оптимизации планов.

Например, вместо соединения миллионов строк двух таблиц, а затем фильтрации по региону, планировщик может сначала оставить только строки нужного региона и соединять уже меньшие наборы.

Это называют проталкиванием предиката (predicate pushdown).

При SQL NULL нужно помнить о трёхзначной логике: строка проходит WHERE только когда условие TRUE; FALSE и UNKNOWN отбрасываются. При этом логика последовательного фильтра и конъюнкции остаётся согласованной.

Для формул с UNION/EXCEPT в классической реляционной алгебре предполагается множественная семантика. В SQL с UNION ALL кратности сохраняются, поэтому алгебраические правила необходимо применять с учётом мультимножественной семантики.
